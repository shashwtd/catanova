# Architecture

## One repository, one distribution

`packages/rules` owns pure game transitions and board generation. `packages/protocol` defines bounded, canonical network messages. `apps/server` authenticates seats, supplies private randomness, commits actions and sends authorized views. `apps/client` renders those views and submits player intent.

The client uses React, a static WebGL 2 terrain layer and an SVG board with bright player-colored pieces. Signed hex masks blend biomes into shared ground; the existing coast has a continuous sea band with gentler outer curves. Mirrored repeats and atlas gutters reduce material seams. The flat camera moves island and walnut tabletop together. Each port has two bridge entrances at its eligible coastal vertices. WebGL draws on load, resize, board changes and context recovery, capped at 2× pixel density, with an SVG fallback and no idle render loop. Accessible legal-site previews lead to a separate placement confirmation; the server remains the final validator. See [art and renderer details](ART.md).

The Node process serves the built client and `/ws` on the same origin. Local play needs one install/build/start flow, and Docker ships both. A CDN can be introduced later without creating separate repositories. React/Vite integration follows the [React client API](https://react.dev/reference/react-dom/client/createRoot) and [Vite build documentation](https://vite.dev/guide/build).

## Game authority and hidden information

The server chooses a public board seed, shuffled seat order, private shuffled development deck, dice and theft outcomes using cryptographic randomness. The public map seed cannot predict the private deck or rolls. `applyAction` clones an input game and returns an accepted next state; rejected actions cannot partially change it. Costs, piece limits, turn phases and scoring are enforced by this transition.

The database stores full authoritative state. `gameView` emits a separate snapshot for every recipient: their own hand/card identities, opponents' counts and visible points, public board, journal, trade and phase. It omits the deck order and opponents' hidden identities. Own hidden victory points count privately; final point totals are visible at victory. The public journal omits resource type stolen and discard mix. Bank counts are currently public for resource selection, so changes can reveal discarded resource mix; this information policy is tracked in the playtest notes. Authentication tokens never appear in snapshots.

## Sessions and command commitment

`create` and `join` reserve one of four seats. The lobby is a separate screen; the host starts with three or four ready, connected players. The first remaining lobby seat hosts the game, and new seats are rejected after start. Each seat has a 256-bit client-generated secret token, stored only as a SHA-256 hash on the server. Repeated handshakes with the same token return the same seat, including when the first response was lost. Resuming replaces and immediately revokes the prior socket.

The server creates and persists the balanced board when the room is created. `GET /api/rooms/CODE` returns only that board, public player identities and whether play has started. The invite route opens a roster and Join prompt without displaying the game board. With a verified Google session, it also reports whether this account already has a resumable seat. Starting the game uses the same board seed; private deck and turn-order randomness are separate. Legacy rooms without a stored preview board acquire one on first access.

A `leave` command atomically marks a lobby seat departed, increments its revision and records the receipt. Departed credentials cannot resume; old receipts remain intact. Leaving after start preserves the seat and game state. The server closes intentional departures with code 4002, which stops automatic reconnection. A lost lobby-leave acknowledgment resolves on resume as `SEAT_LEFT`; the tab clears its pending departure.

With [Supabase authentication](AUTH.md) configured, the verified Google account also owns its seat. A new device can resume that account’s seat through the same invite; its token rotates and the old socket is revoked. Cosmetic profiles are stored against the verified account in SQLite. The profile editor offers a name and one of twelve portraits, displayed with a consistent rounded-square border. The public profile schema retains accent and frame fields for saved-profile compatibility; these are not current customization choices. Supabase anonymous identities are rejected until a guest policy is approved.

Every game action has a UUID command ID, expected room revision and canonical payload. A SQLite transaction checks the receipt and revision, validates the move, saves next state, appends its private event plus public history entry, increments the revision and writes a receipt. A replay with the same ID and payload returns the original result. Reusing an ID with different intent or submitting a stale new action is rejected. The server never silently reinterprets stale game intent. Lobby Ready commands are an explicit per-seat boolean, so independent simultaneous Ready updates can apply from the same observed revision. They retain their own durable deduplication receipts; game moves still require an exact revision.

State, event history and receipt commit **before acknowledgment**. The counter probe uses separate receipts and cannot run inside a started game. Cross-operation ID reuse is rejected. Transactions use WAL plus `synchronous=FULL`. All actions run serially in one server process.

Player trades carry a live offer ID. Fixed offers specify both resource bundles; open offers collect per-opponent return proposals for the active player to choose. Acceptance rechecks the offer, phase and both hands, then saves both transfers in the same action transaction. Replaced, withdrawn or expired offers cannot be accepted. Public proposals reveal only their offered resources; private hands remain filtered.

The client writes the seat and unresolved command to tab session storage before sending them. Refresh/reconnect resends the same command; it does not create a second roll or charge. The explicit last-seat recovery button uses local storage. A closed tab or cleared storage can lose its unresolved outbox. Local playtest credentials can also be lost; Google users can recover the account-owned seat through its invite, but should inspect the saved result before repeating an uncertain move. Never share seat tokens as invites.

## Reconnection and storage limits

Presence is transient and separate from the durable revision. A heartbeat detects dead sockets; the client reconnects with bounded exponential backoff and jitter. On welcome it receives a filtered snapshot and replays unresolved commands after validating it. The client keeps an acknowledged move pending until it installs a snapshot at least as new as the acknowledgment. It ignores stale frames and rejects snapshots that remove roads, lose or downgrade buildings, change the island, or move the turn backwards. A rejected snapshot leaves the last good board visible and blocks new moves while bounded resynchronization runs. An old welcome after server rollback also blocks replay until state catches up. Resync requests are throttled to avoid response loops. Reconnecting a seat does not reserve an extra place. There is no auto-forfeit or bot takeover. When the host enables the optional [turn timer](TURN_CLOCK.md), server-owned deadlines continue through disconnections and restarts.

SQLite stores rooms, seats, account profiles, full games, private game events, paginated public history and command receipts. A three-second application ping records up to 60 round-trip samples, missed probes and reconnects for the connection panel. Those measurements are not a packet-loss estimate or a hosting availability guarantee. Game snapshots carry a schema and ruleset version; unknown schema versions are rejected. It is a **single-process local store**, not a multi-replica cloud database. Tests cover failed writes, abrupt process death, real four-client play, lost replies and restarting after a saved roll. Disk loss, volume deletion, regional failure and restoring old backups are different guarantees.

Every newly accepted game action has a durable event containing its canonical private action, resulting full state (including private random outcomes), state SHA-256, previous state hash, and a filtered public history entry. The ledger and receipt are in the same transaction. The hot snapshot keeps only 80 recent journal lines; history pages the full ledger in batches of 40 and groups the visible entries by turn with action/resource icons. Revisions remain internal keys, not displayed labels. Existing games are imported on their next move with the last journal entries still available; older truncated history cannot be recreated.

The current game snapshot is checked against the latest event’s state hash before use. A mismatch stops further play instead of silently replacing accepted pieces. The ledger provides a second record for operator recovery; it is not a cryptographically authenticated audit trail or an off-machine backup. Deterministic action replay across rules versions, operator repair tooling and full cloud schema migration remain future work. Keep backups of the whole SQLite database, including account profiles and receipts. Do not copy a live WAL database file alone or restore an older snapshot while retaining newer receipts.

The permanent-piece rule is specific to the base game. An expansion that removes or moves pieces will need a versioned state invariant rather than weakening the guard globally.

## Hosted deployment

Use one always-running Azure Container Apps instance with nearby Supabase Postgres for the initial hosted playtest. Serve client assets from that instance first. The Postgres adapter must atomically save state, private event records, chosen outcomes and receipts before responding. Database service credentials never belong in the client.

Postgres, cloud migrations and deployment draining are not implemented yet. Azure's ephemeral filesystem must not be mistaken for durable SQLite storage. One process restarting produces a reconnect window; it is not high availability. Before multiple replicas, implement exclusive room ownership with fencing, room-aware routing and coordinated broadcasts. Sticky sessions alone do not make all players in one room reach the same owner.

Measure acknowledgment p50/p95/p99, reconnect time, frame times, event-loop delay, memory, database commit latency and save failures. Keep private state out of logs. Test backup restore separately, and measure candidate Azure/Supabase region pairs from actual players. [Hosting assumptions](HOSTING.md) and [remaining work](ROADMAP.md) stay explicit.
