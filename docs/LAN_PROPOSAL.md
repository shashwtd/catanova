# LAN play proposal

Proposed, not implemented. Updated 9 September 2026.

**Recommendation:** offer a downloadable Catanova host bundle containing the server, game assets, fonts, sounds, and a local SQLite save database. One laptop runs it; two to four invited players open the game in their browsers on the same Wi-Fi or hotspot. The host shows a QR code and an address such as `http://192.168.1.20:3000`. The host's own browser can use `localhost`; everyone else must use the host's LAN address. No public matchmaking or solo mode is needed.

Internet access would be unnecessary once the bundle is downloaded. A working local connection is still necessary: a router, a laptop hotspot, a phone hotspot that permits device-to-device traffic, or wired Ethernet. Without Wi-Fi, Ethernet, or a hotspot, the devices have no path to each other. Guest-network isolation, hotspot restrictions, or a host firewall can block that path; the host launcher should check connectivity and explain the specific failure. The game should expose a private-network listener only when the user starts LAN hosting.

The package should run the server independently of its browser window and keep its save directory across app updates. Closing a tab must not stop hosting. Use the existing server and rules packages with an explicit LAN identity mode: a locally chosen name/avatar and a separate, random seat credential. Google/Supabase sign-in, friend lookup, remote fonts, analytics, and asset downloads must not be prerequisites. LAN names are local identities, not verified online accounts. The public room QR must never contain someone's private resume token; a separate private recovery code can restore a seat if browser storage or the host address changes. This mode should be separate from the current `auth: null` integration-test setting and must not weaken online authentication.

Each action should follow the existing authority model: the client submits intent with a unique command ID and the expected revision; the server validates it; one transaction stores the resulting state, event, receipt, and revision; only after commit does the server acknowledge and broadcast each player's permitted view. The client retains an unfinished command until the matching authoritative snapshot arrives. Retrying its ID retrieves the saved result instead of placing another road or rolling again. These mechanisms already exist in `apps/server/src/store.ts`, `apps/server/src/server.ts`, and `apps/client/src/connection.ts`; packaging LAN mode must preserve them.

SQLite transactions provide all-or-nothing changes across a crash, subject to the filesystem and hardware honoring their durability guarantees. Our store already uses WAL and `synchronous = FULL`; keep the live database on the host's local disk, not a shared network drive. Provide a consistent backup/export operation rather than copying a live `.sqlite` file alone: committed data can still reside in its WAL. A backup should include the private game state and receipts, be protected accordingly, and never be broadcast to every player as public history. This protects against app/process failure; a failed disk still requires a separate backup. [SQLite atomic commit](https://sqlite.org/atomiccommit.html), [SQLite write-ahead logging](https://sqlite.org/wal.html).

| Interruption                                                 | Proposed behavior                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| One player's browser closes or Wi-Fi drops                   | Mark that seat disconnected. Other clients stay connected and can perform permitted actions; the game may still wait for the absent player's turn or mandatory choice unless the configured timer resolves it. Rejoining restores that seat's private view.                    |
| The host closes only the game tab                            | The separate host process continues serving everyone.                                                                                                                                                                                                                          |
| The host app stops, laptop sleeps, or host loses the network | Everyone loses access to the authority. Show a reconnecting state and keep accepted state saved; do not let clients invent replacement moves.                                                                                                                                  |
| The host restarts with the same save directory               | Reload the committed room, reconnect seats, and reconcile pending commands once. For LAN, pause game time across hosting downtime and require a resume action/grace period, so restarting cannot immediately consume several turns. That timer policy requires implementation. |
| The host device or save disk is permanently lost             | Recover only as far as the latest valid backup. A local event log alone cannot make an unavailable device available.                                                                                                                                                           |

**Plain LAN HTTP needs a deliberate compatibility pass.** A remote `http://192.168...` page does not receive the same secure-context exemption as `http://localhost`. Service workers require a secure context; arbitrary LAN HTTP therefore cannot be the basis of a promised installable offline PWA. Trusted HTTPS needs certificate provisioning and trust on joining devices, not just a self-signed certificate warning. For the first version, browsers can fetch the entire game directly from the local host without a service worker. [MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts), [MDN Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API).

The client currently calls `crypto.randomUUID()`. Before LAN HTTP is supported, audit secure-context APIs and provide suitable alternatives, including generating random command IDs with `crypto.getRandomValues()`, which is available in insecure contexts. Clipboard interactions also need a selectable-address fallback. Plain HTTP leaves traffic, including local seat credentials and hands, unencrypted; restrict that initial option to trusted private networks and keep online account credentials out of it. Secure transport is the stronger subsequent option. [MDN Crypto.getRandomValues](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues).

Downloading the host bundle before going offline is sufficient for the proposed architecture. If an installable client is added later, install and verify its asset cache before losing internet access. A cached game interface still needs the local authority to play; it does not turn a browser into a listening server. Browsers may freeze or discard background pages, and mobile termination callbacks are unreliable. Therefore, save per accepted action and reconnect on return; do not depend on a final unload save or use a phone browser as the first hosting platform. A laptop host should stay awake during play. [MDN Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API), [Chrome Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).

Automatic host migration should be a separate project. It needs replicated committed state, leader election, authority epochs that reject an old host's commands, and protection against two disconnected groups each believing they own the game. Consensus designs separate these responsibilities for good reason; a two-device room cannot safely assume that the other device crashed merely because its messages stopped arriving. [Ongaro and Ousterhout, Raft](https://raft.github.io/raft.pdf). Catanova also has hidden hands, the development deck, and unrevealed randomness: copying full authority state to every ordinary client would expose them. A backup candidate must be explicitly trusted, or a stronger encrypted replication design must be built. The first LAN release should promise durable resume on the same host and manual backup recovery, with no claim of instant failover.

Before shipping, test two-, three-, and four-player rooms with internet disconnected, fresh browser clients fetching all assets from the host, private-view isolation, Wi-Fi interruption, duplicate retries after lost acknowledgements, forced host termination immediately before/after commit, restart from disk, timer resume, changed LAN addresses, and backup restore. Test ordinary HTTP clients and device sleep behavior explicitly. These are proposed LAN acceptance checks; the current two-player production-server integration tests validate the existing multiplayer foundation, not a finished LAN product.
